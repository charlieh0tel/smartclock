# The 58503A over BDM

The bench 58503A's main board (58503-60001 Rev C), running 3704,
measured through its MC68331's (U33) background debug mode (BDM), on
its header J12.  A BDM probe reads what the console cannot, the SIM's
"S" registers among them (`hardware-investigations.md`, "Register
reads through the console"), with the CPU halted in background mode.
The Z3805A's and Z3801A's J12 are not checked.  The probe and its
host tools are the
[mc683xx-bdm](https://github.com/charlieh0tel/mc683xx-bdm) project's;
what was done is given here in the chip's terms.  Step names (R0, W0
and on) are the bench checklist's.

## J12

On the bench 58503A's main board (58503-60001 Rev C), on 2026-11-20,
J12 is the standard header of MC68331UM 5.10.2.8, Figure 5-11.  Pin 2
is the pin nearest the two closest board edges, the corner pin; pin 1
is inboard of pin 2.  Buzzed with the power off:

| Header pin | Signal (Figure 5-11) | Reads |
| ---------- | -------------------- | ----- |
| 1 | DS | not checked |
| 2 | BERR | not buzzed; behaved as BERR in use ("Halting the running firmware") |
| 3 | GND | ground |
| 4 | BKPT/DSCLK | U33 pin 56 |
| 5 | GND | ground |
| 6 | FREEZE | not buzzed; behaved as FREEZE in use |
| 7 | RESET | not buzzed; behaved as RESET in use |
| 8 | IFETCH/DSI | U33 pin 55 |
| 9 | VDD | +5 V |
| 10 | IPIPE/DSO | U33 pin 54 |

Powered, a BDM probe on J12 reset the CPU into background mode and
read the whole flash, which matched the 3704 image.  So BDM access
through J12 is established on that board.

## The clock

At a reset entry SYNCR reads `0x3f08`: W 0, X 0, Y 63 and SLOCK, so
8.39 MHz from the 32.768 kHz reference (MC68331UM 4.3.2), the
8388608 Hz `tools/bdm` reports.  In a halt
of the running firmware it reads `0xcf88`, 3704's `0xcf80`
(`firmware/58503a-3704.md`) with SLOCK, 16.78 MHz.  DSCLK at 1 MHz
worked at both.  At 8.39 MHz DSCLK can be at most 4.19 MHz, a cycle of
at least two system clocks (MC68331UM Table A-7, B5); the pod's bench
notes have this unit working at up to 3 MHz and failing at 3.5 MHz.

## Halting the running firmware

Measured on 2026-11-21.  The running firmware's SIMCR is
`0x014a`: FRZSW and FRZBM clear, so the software watchdog keeps
counting while the CPU is in background mode (MC68331UM 4.2.13,
D.3.1), and SYPCR `0xcc` gives it about 8 s, measured
(`hardware-investigations.md` item 7, "Measured, resets on the
58503A").  A halt of under 1 s and resume left the firmware running
(step R0): RSR unchanged, and `watchdog_countdown` (`0x100b90`;
`firmware/restart.md`, "The watchdog") read `0x0007`.  In that halt
ATEMP read 0, a breakpoint; SYPCR `0xcc`, PICR `0x0542`, PITR
`0x0008`, SYNCR `0xcf88`; RPC `0x000120fc`, PCC `0x000120f8`; RSR
`0x80`, the last reset the probe's.  Writing SIMCR
`0x614a`, FRZSW and FRZBM set, before a long halt froze the watchdog:
a 15 s halt, then SIMCR restored to `0x014a` and resume, with no
reset.  The receiver's log recorded that halt, as it records long
halts, as `Holdover started, invalid GPS 1PPS` (step W0).  The
watchdog's countdown read the same after the halt as before.

FRZBM also stops the bus monitor in background mode, so with it set
an access nothing answers does not end in a bus error.  With `0x614a`
the second single step under a debugger hung the CPU until a probe
reset, likely on an access past the top of RAM, `0x10ffff`; with
`0x414a`, FRZSW alone, steps went through ("Single steps").  Each was
seen once.  BERR driven on J12 pin 2 ends such an access: with
`0x614a` and the probe driving BERR, a read of unmapped `0x110000`
ended in a bus error and the CPU took commands after.  So `0x614a`
for a long halt that touches only mapped addresses, `0x414a` for
stepping.

## With background mode off

A reset with BKPT high leaves background mode off: a power-up, a
watchdog reset (`hardware-investigations.md` item 7), or a reset from the
probe released to run.  A halt asked for then is a breakpoint
exception, vector 12, which the firmware does not survive
(`firmware/restart.md`, "The watchdog"): the halt monitor resets the
CPU, RSR `0x10`, and BKPT, still held low by the probe at that reset,
enables background mode.  The CPU then halts at the reset vector,
RPC `0x550`, not where the firmware was.

## Single steps

On 2026-11-21, from a halt of the running primary at `0x133ee`, SIMCR
`0x414a` for the session, a scratch block at `0x106000`: the first
trace step took a pending level-6 interrupt and stopped at its
handler's entry, `0x12fb2`, SR `0x2600`, SP `0x10fcf8`; the next two
stepped inside the handler.  VBR read `0x10000`, the primary's table,
and the firmware ran on when released.  Steps and breakpoints in RAM
need the RAM's selects, CS0, CS2 and CS3, which a reset entry has not
set ("At a reset entry").

## At a reset entry

BKPT held low at reset, so that the CPU enters background mode before
its first instruction; measured on 2026-11-21.  SIMCR reads `0x60cf`
and SYPCR `0x80`: the watchdog is frozen in background mode until the
firmware rewrites SIMCR.  MC68331UM D.3.1 gives FRZSW and FRZBM as 0
at reset; why they read 1 here was not established.  CSPAR0 reads
`0x3fff`, CSPAR1 `0x03ff`, CSBARBT `0x0007` and CSORBT `0x7b70`: only
CSBOOT is set up, as a 1 MiB block, so `0x40000` mirrors the lower
bank until the chip selects are set.  The rest, read before the
first instruction:

| Register | Value |
| -------- | ----- |
| ATEMP | 0, a breakpoint |
| RPC | `0x00000550`, the reset vector's entry |
| SSP | `0x0010fffe`, the reset vector's stack |
| SR | `0x2714` |
| PCC | `0xffffffff` |

The code at `0x550`, the boot code, begins `move.w #0x2700,sr`,
`movea.l #0,a0`, `movec a0,vbr` (`0x4e7b 0x8801`), `movea.l (a0),sp`
and `move.b #0xcc,0xfffa21`, SYPCR, before the chip selects
(`firmware/chip-selects.md`, "58503A 3704"); after it VBR read 0 and
SSP `0x10fffe`, the vector at 0.

SYPCR takes one write after a reset (MC68331UM D.3.12): from a reset
entry, writing it `0x00` first disabled the watchdog for running test
code.

RSR reads the reset's cause (`hardware-investigations.md` item 7): `0x80`
after the probe's reset, `0x40` after a power-up into background mode,
BKPT held low through the power cycle, and `0x20` after a watchdog
reset with BKPT held low through it.  That reset too entered background
mode at the reset vector: ATEMP 0, SIMCR `0x60cf`, SYPCR `0x80`, RPC
`0x550`, VBR 0.

*Open:* after a halt with the firmware's chip selects set and a GO, the
CPU once left background mode by itself within a few commands, RSR
then `0x10`, a halt-monitor reset (MC68331UM D.3.4); the boot code's
SYPCR `0xcc` enables the halt monitor.  Reading from a reset entry
avoids it.

## The chip selects

Measured on 2026-11-20.  With the firmware run 3 s and halted, every
chip-select register read as `firmware/chip-selects.md`'s tables for
the 58503A 3704 give it, so those tables are confirmed on silicon
for this board: CSPAR0 `0x2bff`, CSPAR1 `0x03af`; CSBARBT, CSORBT
`0x0005`, `0x6870`; CS0 `0x1003`, `0x6830`; CS1 `0x0405`, `0x6870`;
CS2 `0x1003`, `0x5030`; CS3 `0x1003`, `0x3030`; CS4 0, 0; CS5
`0x3003`, `0x7b30`; CS6 `0x0005`, `0x7070`; CS7 `0x0405`, `0x7070`;
CS8 `0x2000`, `0x3bf0`; CS9 `0x4001`, `0x78f0`; CS10 `0xfff8`,
`0x2bc4`.

## Reading the flash

At a reset entry only CSBOOT is set, as a 1 MiB block, so `0x40000`
reads the lower bank again ("At a reset entry").  Writing CSBARBT
(`0xfffa48`) `0x0005`, 256 KiB at 0, then CSBAR1 (`0xfffa50`)
`0x0405` and CSOR1 (`0xfffa52`) `0x6870`, both bytes, read, one wait,
as the boot code sets them (`firmware/chip-selects.md`, "58503A
3704"), maps both banks; `0x0` to `0x7ffff` then read the same as
`third_party/firmware/images/58503a-3704.bin`, byte for byte
(2026-11-20).

## Programming the flash

On 2026-11-21, from one reset entry, the firmware never run (stages A
to C of the flash procedure).  The chip selects first as the boot
code sets them, CSORBT `0x6870` before any write: each part's /WE is
its bank's write select, CS6 or CS7, and its /OE the read select,
CSBOOT or CS1 (`firmware/restart.md`, "The chip selects"), so a write
through the reset state's CSORBT, `0x7b70`, read and write, programs
nothing but drives the parts' outputs against the CPU's.  Then CS6
`0x0005`, `0x7070` and CS7 `0x0405`, `0x7070`, the write selects.

Each command word carries the command in both bytes, one per part of
the pair, at the bank's base plus twice the parts' unlock addresses,
as the installer writes them (`firmware/restart.md`, "The
installer"): `0xaaaa` to base + `0xaaaa`, `0x5555` to base +
`0x5554`, then the command to base + `0xaaaa` (Am29F010B data sheet,
`third_party/amd/Am29F010B.pdf`):

| Command | Word | Result |
| ------- | ---- | ------ |
| Autoselect | `0x9090` | `0x0101` at base, the manufacturer, and `0x2020` at base + 2, the device, in both banks: four Am29F010s; at each sector pair's `0x8000` × n + 4, protection, `0x0000`, all sixteen pairs unprotected |
| Read/reset | `0xf0f0` | back to reading the array |
| Program | `0xa0a0`, then the word at its address | `0x5aa5` at `0x70000`, read back at once |
| Sector erase | `0x8080`, the unlock again, then `0x3030` at the sector pair | `0x70000` erased in 0.48 s, `0x78000` in 0.52 s |

`0x78000`'s pair holds the upper bank's stored lane sums; after its
erase they were programmed back, `0xbcae` at `0x7fffc` and `0x0c74`
at `0x7fffe`.  The whole 512 KiB then read as the 3704 image again,
and released from reset the primary booted and locked
(`hardware-investigations.md` item 13, "Measured, flash over J12 on
the 58503A").  `tools/bdm` now does this with a routine run from RAM,
first tried on the bench on 2026-11-22
([`tools/bdm/README.md`](../tools/bdm/README.md), "Seen on the bench").
